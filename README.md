장편 역사소설을 LLM과 장기간 공동 집필하면서 겪은 시행착오와, 그 과정에서 발전한 state management, version control, validation, workflow 운영 방식을 정리한 작업 회고입니다.

# 마거릿 프로젝트 작업 회고  
## 장기 LLM 창작에서 기억보다 어려웠던 것들

### 들어가며

이 글은 장편 역사소설 프로젝트 **〈마거릿 이야기〉**를 인간과 LLM이 함께 집필하면서 겪은 시행착오를 정리한 작업 회고입니다.

처음에는 아주 단순했습니다. 사람이 소재와 상황을 던지고, LLM이 장면과 대사를 확장했습니다. 사람이 결과를 읽으며 시대적 개연성, 인물의 행동, 관계의 속도, 말투와 분위기를 교정했습니다.

하지만 이야기가 길어지고 등장인물이 늘어나자 문제는 더 이상 “문장을 잘 쓰는가”에 머물지 않았습니다.

- 무엇이 현재 정본인가
- 무엇이 폐기된 아이디어인가
- 지금 이 인물은 무엇을 알고 있는가
- 과거 사건과 현재 상태가 충돌하지 않는가
- 모델이 지금 초고 작성 중인지, 설정 검토 중인지, 복구 작업 중인지
- 수정 한 줄 때문에 이미 맞는 부분까지 다시 깨지지 않는가
- 언제 한 회차를 완전히 닫았다고 볼 것인가

프로젝트가 진행될수록 핵심 문제는 **프롬프트 작성**에서 **상태 관리, 버전 관리, 검증, 워크플로 운영**으로 이동했습니다.

최종적으로 가장 크게 남은 결론은 다음과 같습니다.

> **Long context capacity ≠ long-term state management.**  
> 긴 컨텍스트를 제공할 수 있다는 것과, 장기 프로젝트의 상태를 안정적으로 관리할 수 있다는 것은 같은 문제가 아닙니다.

---

# 1. 시작: 자유 탐색과 `manuscript as state`

초기에는 별도의 정교한 설정 시스템이 필요하지 않았습니다.

작업 루프는 대체로 다음과 같았습니다.

`사용자의 고밀도 아이디어 → LLM의 장면 확장 → 인간의 세계·사회·캐릭터 교정 → 즉시 반영`

이 단계에서 중요한 발견은 **캐릭터가 설정표만으로 완성되지 않는다는 점**이었습니다.

캐릭터는 여러 상황에 반복해서 투입되면서 점차 수렴했습니다.

`상황 → 반응 → 반복 패턴 → 캐릭터 모델 수렴`

자유로운 잡담과 가벼운 시뮬레이션은 낭비가 아니었습니다. 오히려 정식 집필 전에 캐릭터의 행동 모델을 만드는 테스트베드 역할을 했습니다.

초기에는 원고 자체가 사실상 상태 저장소였습니다.

`manuscript = state`

세계가 작을 때는 충분히 잘 작동했습니다. 그러나 세계가 커진 바로 그 성공 때문에 이후에는 별도의 상태 관리가 필요해졌습니다.

### 첫 번째 교훈

> **아이디어 탐색과 정식 집필은 분리하는 편이 좋습니다.**  
> 핵심 인물을 본편에 바로 투입하기보다, 안전한 공간에서 충분히 행동시켜 본 뒤 캐릭터가 수렴하면 집필 속도와 일관성이 크게 좋아집니다.

---

# 2. Story Bible의 등장과 첫 번째 부작용

세계가 커지면서 원고만으로는 더 이상 충분하지 않았습니다.

등장인물이 늘고, 각 인물이 서로 다른 정보와 관계 상태를 가지기 시작했습니다. 그래서 별도의 Story Bible을 만들었습니다.

`manuscript + story bible = state`

처음에는 매우 효과적이었습니다. 그러나 통합 문서가 커지자 새로운 문제가 생겼습니다.

한 문서 안에 다음 정보가 섞이기 시작했습니다.

- 현재 정본
- 과거 사건
- 미래 구상
- 후보 설정
- 인물 해석
- 역사 조사
- 이미 폐기된 전개

문제는 정보량이 아니라 **authority가 다른 정보가 같은 문서에 있다는 점**이었습니다.

특히 위험했던 것은 이른바 **stale future contamination**이었습니다.

과거에 한때 검토했던 미래 전개가 이후 폐기되었는데도, 모델이 그것을 “기억하고 있는 정보”로 다시 끌어와 현재 사실처럼 사용하는 일이 생겼습니다.

즉 장기 프로젝트에서 위험한 것은 망각만이 아니었습니다.

> **모델이 기억하지 못하는 것도 문제지만, 더 이상 유효하지 않은 것을 기억하는 것도 문제입니다.**

이때부터 최신 정본과 스타일 참고 자료의 역할도 분리하기 시작했습니다.

- 최신 정본: **state anchor**
- 대표 회차: **style anchor**

### 두 번째 교훈

> **더 많은 context가 항상 더 정확한 context를 의미하지는 않습니다.**  
> authority가 다른 정보가 한 입력에 섞이면 오히려 신뢰도가 떨어질 수 있습니다.

---

# 3. 외전에서 드러난 문제: “창작하지 말아야 할 때”

외전을 쓰면서 새로운 유형의 문제가 나타났습니다.

과거가 비어 있는 구간에서는 LLM의 창작 능력이 장점이었습니다. 하지만 본편에서 이미 확정된 사건을 다른 인물의 시점으로 다시 쓰기 시작하자 성공 조건이 완전히 달라졌습니다.

이때의 목표는 다음이었습니다.

> **본편을 한 치도 바꾸지 않으면서 새로운 의미만 추가할 것.**

같은 사건을 다른 시점에서 다시 다루려면 다음을 모두 보존해야 했습니다.

- 사건
- 대사
- 행동
- 순서
- 정보 경계

새로 추가할 수 있는 것은 인물의 내적 해석뿐이었습니다.

그러나 LLM은 해석을 새로운 사건으로 확장하는 경향이 있었습니다.

`새 심리 → 새 대사 → 새 행동 → 새 인과 → 원본과 다른 세계`

여기서 중요한 원칙이 나왔습니다.

> **심리 해석은 canon 위의 annotation이지 specification change가 아닙니다.**

또 하나의 문제는 **knowledge-state leak**이었습니다.

모델은 작품 전체를 알고 있지만, 등장인물은 그렇지 않습니다.

그래서 인물별 정보 상태를 나누기 시작했습니다.

- 직접 목격
- 전달받음
- 근거 있는 추론
- 아직 알 수 없음

특히 똑똑한 캐릭터일수록 “이 정도면 눈치챘겠지”라는 이유로 사실상 전지적 인물처럼 쓰기 쉬웠습니다.

### 세 번째 교훈

> **동일 사건·다른 시점 외전은 기본 전략으로 삼기 어렵습니다.**  
> 가능하면 비어 있는 시간대에서 시작하고, 정본 접속 지점을 최소화하는 편이 안전합니다.

# 4. 승인본을 잃어버리면서 배운 버전 관리

한 회차에서는 장면별로 문장을 승인해 놓고, 나중에 전체를 다시 합쳤습니다.

문제는 “합쳐 달라”는 요청이 단순 결합이 아니라 새로운 생성으로 해석되었다는 점이었습니다.

그 결과:

- 승인 문장이 사라지고
- 이전 표현이 다시 살아나고
- 새 연결 문장이 생기고
- 일부 장면이 축약되거나 누락되고
- 빈틈이 새로운 문장으로 채워졌습니다

이 사건 이후 작업 원칙이 명확해졌습니다.

> **대화창은 원고 저장소가 아니라 회의실입니다. 파일이 원본입니다.**

또한:

> **합본은 새로운 generation이 아니라 잠긴 장면을 순서대로 결합하는 build 작업이어야 합니다.**

권장 우선순위도 정리했습니다.

1. 잠긴 scene file
2. manifest
3. merged file
4. chat record

장편 작업에서 “채팅에 있었던 문장”과 “정본으로 저장된 문장”은 전혀 다른 상태로 다뤄야 했습니다.

---

# 5. 신규 캐릭터: 설정표보다 먼저 필요한 것

새 시즌에서는 기존 캐릭터가 거의 없는 상태에서 많은 인물을 새로 만들어야 했습니다.

이때 발견한 것은 **캐릭터 설정표만으로는 실제 장편 투입이 어렵다**는 점이었습니다.

예를 들어 새로운 의학 인물을 만들 때 단순히 성격과 외모만 정하면 충분하지 않았습니다.

다음과 같은 질문에 답해야 했습니다.

- 처방 권한이 있는가
- 수술 결정권이 있는가
- 군 명령권이 있는가
- 누구의 지휘를 받는가
- 어떤 경로로 고용되었는가
- 어떤 언어를 사용할 수 있는가
- 무엇을 잘하는가
- 무엇은 절대로 할 수 없는가

즉 캐릭터의 personality만 아니라 **permission model과 capability ceiling**이 필요했습니다.

공학적으로 표현하면 prototype을 production에 넣기 전에 schema와 RBAC를 안정화하는 과정에 가까웠습니다.

또 설정 문서에 어떤 규칙을 적어 놓았다고 해서 모델이 반드시 그 규칙을 따르는 것도 아니었습니다.

예를 들어 말투와 호칭을 설정에 적어도 실제 생성에서는 흔들렸습니다.

결국 중요한 설정은 다음 단계를 거쳐야 했습니다.

`문서화 → 생성 전 constraint → 생성 후 validation`

### 네 번째 교훈

> **설정은 모델에게 정보를 제공할 뿐, 행동을 강제하지 않습니다.**  
> 중요한 규칙은 생성 전 제약과 생성 후 검증까지 포함해야 합니다.

---

# 6. 거대한 설정집을 버리고 역할별 상태로 분해하기

통합 설정집이 계속 커지면서 retrieval과 drift 문제가 커졌습니다.

결국 파일을 단순히 크기 기준으로 자르는 대신 **정보의 역할**에 따라 분리했습니다.

예를 들면:

- 핵심 정본
- 현재 상태
- 인물별 설정
- 세계관
- 회차 정본
- 향후 전개
- 후보/미확정
- 폐기/충돌 방지
- 설정 인덱스

핵심은 **role-based partitioning**이었습니다.

특히 유용했던 것은 `현재상태` 파일이었습니다.

모든 과거 사건을 매번 다시 읽는 대신 현재 필요한 상태만 작은 파일로 유지했습니다.

- 날짜와 장소
- 인물 위치
- 업무
- 부상·질병
- 소지품
- 관계 단계
- 진행 중인 사건
- 미회수 약속이나 질문

완료된 사건은 회차 정본으로 이동했습니다.

구조는 사실상 다음과 같았습니다.

`event log + current snapshot`

다만 분산 구조는 새로운 동기화 문제를 만들었습니다.

그래서 정본 확정 이후 state update를 하나의 transaction처럼 다루기 시작했습니다.

1. 확정 본문 저장
2. 회차 사건 추가
3. 현재 상태 갱신
4. 지속 설정 반영
5. 실현된 미래 항목 제거
6. 충돌 검사
7. 인덱스 갱신

### 다섯 번째 교훈

> **Long context capacity ≠ long-term state management.**  
> 중요한 것은 얼마나 많이 넣을 수 있는지가 아니라, 지금 필요한 authoritative state를 얼마나 높은 밀도로 공급하는가입니다.

# 7. 현재 상태만 맞아서는 부족했습니다

이야기가 길어지면서 또 하나의 문제가 드러났습니다.

현재 인물의 위치와 관계가 모두 맞더라도 전체 이야기가 엉뚱한 방향으로 갈 수 있었습니다.

그래서 consistency를 두 종류로 나누었습니다.

- **State consistency:** 지금 가능한가?
- **Trajectory consistency:** 지금 일어나야 하는가?

예를 들어 특정 장면이 설정상 가능한 사건이라도, 전체 서사의 방향과 맞지 않으면 발생해서는 안 됩니다.

이때부터 상위 플롯은 개별 설정보다 높은 수준의 trajectory constraint로 사용되었습니다.

또 언어, 통역, 전달 경로가 복잡해지면서 **character knowledge state**가 독립적인 검증 축이 되었습니다.

각 장면마다 다음을 따져야 했습니다.

- 누가 직접 들었는가
- 누가 통역했는가
- 누가 전달받았는가
- 누가 아직 모르는가

---

# 8. 역할 분리: 초고팀과 설정팀

프로젝트 후반에는 작업 역할을 분리했습니다.

- 초고팀: scene generation
- 설정팀: adversarial continuity review

이 구조는 효과가 좋았습니다.

그러나 새로운 문제가 생겼습니다.

역할을 한 번 부여했다고 해서 모델의 **작업 모드가 영구히 유지되지는 않았습니다.**

설정 검토를 마친 뒤 잡담으로 넘어갔는데도 모델이 계속 설정 보간을 하거나, 복구 작업을 끝냈는데도 repair mode가 남아 사용자의 가벼운 말을 추가 검증 지시처럼 해석하는 일이 있었습니다.

이를 다음과 같이 정리했습니다.

`Task boundary drift → 최초 보간 → 사용자 정정 → correction amplification → 신규 보간`

여기서 나온 중요한 결론은 다음과 같습니다.

> **데이터 상태뿐 아니라 작업 모드도 state입니다.**

초고, 검토, 복구, 잡담, 종료를 명시적으로 구분해야 했습니다.

---

# 9. 정확하지만 너무 비싼 프로세스

정합성 검증을 강화하자 정확도는 높아졌습니다.

하지만 처리 비용이 급격히 커졌습니다.

여러 회차를 묶어 한 번에 정리하면 마지막 회차에서 다음 작업이 한꺼번에 몰렸습니다.

- 최근 회차 정합성 점검
- 날짜·위치·관계·지식·소품 검증
- 회차 정본 갱신
- 현재 상태 갱신
- 지속 설정 갱신
- 미래 항목 제거
- 폐기 충돌 검사
- 인덱스 갱신
- 외부 저장소 반영

기능적으로는 정확했지만 운영적으로는 지속 가능하지 않았습니다.

결론은 명확했습니다.

> **정확하지만 감당할 수 없는 프로세스는 좋은 프로세스가 아닙니다.**

정합성 workflow는 오류율뿐 아니라 다음도 고려해야 합니다.

- context 사용량
- tool call 수
- quota
- 인간 검토 시간
- 인지 피로

이후에는 큰 batch를 줄이고 **회차별 작은 closure**로 이동했습니다.

---

# 10. 후반부: 기술보다 인간 에너지가 병목이 됐습니다

프로젝트 후반에는 오히려 시스템이 가장 안정적이었습니다.

정본 저장, 상태 갱신, 검증, 종료 절차가 거의 루틴화되었습니다.

하지만 다른 문제가 생겼습니다.

캐릭터가 너무 잘 고정된 것입니다.

수십 회차 동안 반복 시뮬레이션된 인물은 이제 작가가 원하는 방향으로 쉽게 움직이지 않았습니다.

작가가 “이제 고백하면 되지 않을까”라고 생각해도, 그 캐릭터가 그렇게 행동하지 않을 것 같으면 설정 검토에서 막혔습니다.

이 단계에서 질문은 더 이상:

> “무슨 사건을 만들까?”

가 아니었습니다.

대신:

> “이 캐릭터를 깨지 않고 한 칸 어떻게 이동시킬까?”

가 되었습니다.

여기서 매우 유용했던 원칙은 다음이었습니다.

> **강하게 고정된 캐릭터를 억지로 움직이지 말고, 그 캐릭터가 자기답게 반응할 수밖에 없는 환경을 바꿉니다.**

즉 `character change`가 아니라 `environment change`입니다.

또 하나의 흥미로운 변화가 있었습니다.

초기에는 사람이 모델의 character drift를 막았습니다.  
후기에는 구축된 캐릭터 모델이 오히려 인간의 서사적 지름길을 막았습니다.

### 여섯 번째 교훈

> **장기간 반복 시뮬레이션된 캐릭터의 행동 모델 자체가 정본의 일부가 됩니다.**

---

# 11. 가장 편하게 굴러간 외전의 조건

프로젝트 마지막 외전은 이전보다 훨씬 수월했습니다.

이유는 두 가지였습니다.

- 캐릭터가 이미 충분히 확정되어 있었고
- 기존 정본과 강하게 얽히지 않는 시간대를 사용했습니다

이를 다음처럼 정리할 수 있습니다.

> **high character certainty + low canon coupling**

이 조건에서는 캐릭터 자체가 다음 장면을 만들어 냈습니다.

작가가 매번 새로운 사건을 억지로 주입하지 않아도, 그 인물의 성격과 자기기만, 습관, 관심사가 다음 에피소드의 동력이 되었습니다.

여기서 나온 창작 쪽 결론은 다음과 같습니다.

> **좋은 캐릭터는 plot을 소비하지 않고 생성합니다.**

그리고 장기 프로젝트에서 중요한 것은 정합성만이 아니었습니다.

> **탐색 가능한 자유 공간을 의도적으로 남겨야 창작 에너지가 유지됩니다.**

# 12. 실패 유형 정리

프로젝트에서 반복된 주요 오류는 다음과 같습니다.

1. 이름 오염  
   서로 다른 인물의 이름이나 성을 합성해 잘못 생성하는 문제

2. 호칭 drift  
   이미 확정된 호칭 규칙이 흔들리는 문제

3. scene-state regression  
   장면이 이미 이동했는데 이전 상태로 되돌아가는 문제

4. 계절·환경 충돌  
   현재 계절이나 장소와 맞지 않는 환경 묘사

5. knowledge leakage  
   정보 경로가 없는 인물이 어떤 사실을 알고 있는 문제

6. meta leakage  
   본문 안에 회차 번호나 작업 메타 정보가 들어가는 문제

7. relative-time 오류  
   “지난주”, “지난번”처럼 기준 시점이 잘못 연결되는 문제

8. 역사·사회적 choreography 오류  
   시대의 관습과 인물 행동이 충돌하는 문제

9. 감정 과설명  
   장면이 이미 보여준 감정을 서술자가 다시 설명하는 문제

10. stale branch contamination  
    폐기된 후보가 다시 정본처럼 살아나는 문제

11. handoff/recheck overhead  
    역할 분리 뒤 인수인계 비용이 커지는 문제

12. 인간 수정 뒤 모델이 되돌리는 문제  
    사용자가 직접 고친 문장을 모델이 다시 “개선”해 원복하는 문제

13. 작은 patch 때문에 전체를 다시 생성해 collateral regression이 생기는 문제

---

# 13. 수정 severity에 따라 검증 범위를 다르게

모든 수정에 같은 수준의 QA를 적용하면 비용이 너무 커집니다.

그래서 수정 종류에 따라 검증 범위를 구분하는 방식이 유효했습니다.

- **P0 — continuity / knowledge / history contradiction**  
  관련 dependency 전체 재검증

- **P1 — characterization / scene logic**  
  해당 구간 중심 targeted recheck

- **P2 — wording / style**  
  local patch + 변경 구간 확인

- **P3 — typo / spacing**  
  직접 수정

특히 “이 부분만 고쳐 달라”는 요청을 단순한 말투가 아니라 **change-set boundary**로 취급하는 것이 중요했습니다.

작은 수정 때문에 전체 회차를 다시 생성하면 이미 맞는 문장까지 깨질 가능성이 커집니다.

# 14. 다음 장기 프로젝트를 위한 SOP

이 프로젝트를 다시 시작한다면 다음과 같은 구조를 처음부터 사용하게 될 것 같습니다.

## 0. Project Bible
절대 고정값만 유지합니다.

- 이름 / ID
- 호칭
- 시대 기본값
- 절대 금지

## 1. Arc State
현재 시즌의 상태를 별도로 유지합니다.

## 2. Character Simulation
핵심 신규 인물이 아직 충분히 느껴지지 않으면 본편을 시작하지 않습니다.

본편 밖 안전한 공간에서 충분히 행동시킨 뒤 설정을 추출합니다.

## 3. Episode Contract
회차마다 최소한 다음을 정의합니다.

- entry state
- purpose
- must happen
- must not happen
- exit target
- POV
- location / time

## 4. Draft
작업에 필요한 working set만 읽습니다.

## 5. QA
검증을 분리합니다.

- Continuity QA
- Historical QA
- Character QA
- Prose QA
- Meta QA

## 6. Patch
구조적 문제가 아니라면 affected span만 수정합니다.

## 7. Human Acceptance
인간이 직접 수정한 문장은 가장 높은 authority로 취급합니다.

## 8. Canonical Lock
정본을 확정합니다.

## 9. State Delta
이번 회차에서 변한 사실, 지식, 관계, 소품만 갱신합니다.

## 10. Archive
옛 draft와 rejected branch는 active context에서 제거합니다.

## 11. CLOSED
명시적으로 reopen하기 전에는 다시 건드리지 않습니다.

# 15. 인간과 LLM의 역할

프로젝트가 끝날 무렵 역할은 꽤 명확해졌습니다.

## 인간

- 세계의 사회적·윤리적 물리 결정
- 캐릭터가 자기다운지 판정
- 무엇을 살리고 버릴지 선택
- 서사 방향과 감정선 최종 결정
- authority hierarchy 설정
- QA 기준 설계
- 최종 acceptance
- 언제 충분한지 판단하고 닫기

## LLM

- 장면, 대사, 연결 prose 고속 생성
- 캐릭터 반복 시뮬레이션
- 설정 후보 구조화
- 역사·세계관 제약과 fiction 연결
- structured state 갱신
- adversarial QA
- 반복 패턴과 failure mode 추출

후반으로 갈수록 인간은 단순한 문장 생성자보다 **system architect + creative authority + acceptance tester**에 가까워졌고, LLM은 **generator + validator + state operator**로 분화되었습니다.

# 16. 최종 결론

이 프로젝트를 통해 가장 크게 배운 점은 장기 LLM 창작의 핵심 문제가 단순한 기억 용량이 아니라는 것이었습니다.

중요했던 것은 다음을 계속 명확하게 유지하는 일이었습니다.

- 무엇이 진실인가
- 지금 무엇이 활성 상태인가
- 누가 무엇을 알고 있는가
- 무엇을 절대로 바꾸면 안 되는가
- 지금 모델이 어떤 역할을 수행 중인가
- 언제 작업이 끝났는가

시스템의 진화는 대체로 다음 순서로 진행되었습니다.

`prompting → memory → state management → version control → validation → workflow orchestration → cost optimization → human-energy management`

그리고 창작 쪽에서는 또 하나의 결론이 남았습니다.

> **좋은 캐릭터는 설정표에서 완성되지 않습니다. 충분히 오래 행동시켜서 “이 사람은 이제 작가가 밀어도 자기답지 않은 방향으로는 움직이지 않는다”는 순간이 오면, 그 행동 모델 자체가 정본의 일부가 됩니다.**

장기 LLM 협업에서 중요한 것은 모델에게 더 많이 기억시키는 것만이 아니었습니다.

**무엇을 기억하게 할지, 무엇을 버릴지, 무엇을 잠글지, 언제 검증할지, 그리고 언제 멈출지를 설계하는 것이 더 중요했습니다.**
